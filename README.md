
# midpoint-find

## 1. サービス概要（※最後に書いてOK）
複数人のそれぞれの出発地（駅や拠点）を入力するだけで、一番遠い2人の負担を考慮した中間地点を算出し、その周辺の飲食店もまとめて確認・提案できるアプリ。

- 誰の、どんな課題を、どう解決するか
勤務地や拠点が違う友人同士と飲み会の場所決めで行う「どこで集まるか」を考える面倒な作業を減らしたい。

---

## 2. このアイデアはどこから生まれたか
仲良い前職の人達と集まったり、友人とご飯を食べたい時にどこに行くのか考えるのが大変だったため。
例えば、仕事終わりなどに飲みに行きたいけど場所の調整するフェーズで今日は辞めとくかとなってしまったため。

### 2-1. きっかけとなった体験・感情

このアイデアの元になった
**自分自身の体験・感情・違和感**を教えてください。

- いつ
飲みに行く時、定期的に集まる時

- どんな状況で
客先や拠点がバラバラで、毎回「どこで飲むか」を相談して決めている最中に使える。

- どんな気持ちになったか
「前回の人は遠かったから今回はこっち寄りにしよう」と気を使ったり、移動経路を一人ずつ調べたりするのが地味に面倒で、「もっと楽に決まる方法はないかな」と感じた。

できるだけ具体的なエピソードで書いてください。
SESをしているため、各々拠点が違いどこから来るのかが時期で変わる。
そのため、毎回どこで飲もうかを考えるのが少し面倒だった。

---

### 2-2. なぜそれが「気になった」のか

全体で集まる時に、特定の1人だけ移動時間がずば抜けて長くて大変そうだったり、店決めまでに何度もLINEでやり取りして時間がかかったりした経験がある。
コミュニケーションのハードルや、無駄な調整コスト（心理的・時間的コスト）はできる限り減らして、純粋に集まる時間を楽しみたい。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

その体験の中で、最初に感じた「困りごと」は何ですか？

小さなめんどくさいこと（「どこで集まる？」「誰がどこから来るんだっけ？」という場所決めのやり取り）を減らしたい

---

### 3-2. 本当に解決したい課題は何か

「なぜそれが困るのか？」を**最低3回**繰り返してください。

- なぜ？
場所決めが面倒なこと。

- なぜ？
お互いの正確な出発地が分からないまま「どこにしよう」と探すため、精神的疲労が発生すること。※1決定疲労（Decision Fatigue）

- なぜ？
みんな来る場所がバラバラで、「誰に合わせればいいんだっけ…」って考えながら探すだけで、仕事終わりとかだと余計に頭が疲れてきちゃうこと。※2取引コスト（Friction Cost） / 現状維持バイアス

→ 本当に解決したい課題：集まれれば楽しいのは分かっているが、仕事終わりの疲れた体に場所決めの調整というめんどくささが勝ち、『もう今日はやめとくか…！』と集まるのを諦めてしまう。もったいない瞬間をなくして、もっと気軽に人と会えるようにすること。

- なぜなぜと課題は下記の心理要素を参考に記載しました。
※1決定疲労（Decision Fatigue）： 「どこにする？」って考えるだけの細かい決断の連続で、脳のエネルギーがすり減っちゃう現象。
※2取引コスト（Friction Cost） / 現状維持バイアス： 会う楽しさよりも、そこに至るまでの気疲れや手間のほうが重く感じちゃって、無意識に「動かない（＝会わない）」を選んじゃう心理。

※「アプリでできそうなこと」ではなく
※「人の行動・感情の問題」になっているか確認してください。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

身内の飲み会（9人で定期的に飲んでっているので）

**注意：ターゲットは狭く絞ってください。**

年齢設定：
  - 年齢：20-30代
  - 理由：仕事帰りに定期的に飲みに行ったり、休日に違う場所から集まるための調整の手間を一番「効率化したい」と感じる

生活・状況設定：
  - 生活・状況：勤務地が変わりやすい人、突発的に飲みたいと思う人など。
  - 理由：勤務先や活動拠点が時期によって変わるため、毎回「どこ集合にするか」の前提が変わり、従来の固定化された場所決めが通用しにくいため。

環境設定：
  - 環境：定期的に友達と会う環境、コミュニティがある人。
  - 理由：毎回同じメンバーで集まるからこそ、「前回の場所の履歴」や- 「メンバーごとの今の拠点」を踏まえてスマートに決めたいというニーズがある。

## 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

### 5-2. それでも自分が作りたい理由

既存サービスがある中で、

- なぜ満足できなかったのか
- どこに違和感があったのか

を**自分の言葉**で書いてください。

既存の集合駅検索ツールは「中間にある駅を割り出す」という機能自体はあるものの、あくまで「駅を出すだけ」で終わってしまう点に物足りなさを感じた。

実際に使ってみると、中間駅が分かったあとに「じゃあその駅の周辺でどのお店にするか？」を探すために、わざわざ別アプリ（食べログやGoogleマップ）をもう一度開いて、駅名を打ち直して。という二度手間が発生する。

そのため、算出した中間駅名と連動してグルメサイトの検索結果ページへのリンクが自動作成される機能などを組み合わせ、「場所決めから店探しまでの動線が1つのアプリ内でシームレスに完結する体験」を自分で作りたいと思った。

## 7. このアプリで実現すること

### MVPで作る機能
- ユーザー登録・ログイン機能
- イベント（集まり）の作成機能
- 各メンバーの出発地（駅名）の登録機能
- - 1回目： 飲み会メンバーの入力をする。
  - 2回目： 保存されたメンバーのスタート位置を呼び出して使用する（幹事の入力コストを下げる）。
- 登録されたデータをもとに、一番遠い2人の出発地中間に近い駅を算出する機能
- - 理由：9人で移動時間に偏りがない地点は存在しないため、移動距離の総和を最小化するポイントを割り出すのが最も合理的であるため。
- 「幹事が駅と店の候補をまとめて確認し、仲間へ提案できる」仕様
- - ※理由：飲み会の時、幹事が店まで決めてLINEグループで報告し、「今ここにいるから場所変えられる？」といったやり取りを行う実態に合わせ、アプリ内での過剰な出欠・調整機能は省くため。
- Places APIを連携させた、一番遠い2人の出発地の中間地点周辺の飲食店（居酒屋・カフェなど）の自動レコメンド機能(※APIの無料枠および予算上限・クォータ設定を厳重にかけた上で、MVPの段階から「場所決めから店探しまでのシームレスな体験」を検証する)

### 本リリースで作る機能
- Google Maps API等を用いたマップ表示・ピン留め機能
- 過去の開催履歴や、メンバーごとの移動負担の蓄積・調整機能

## 9. 今後の展開・発展の方向性

### 今考えている発展案

- 機能追加の方向性：
①都市部では電車移動が主流だが、地方出身なので駅の検索ではなく車での中間地点を割り出したりする。

②中間地点の飲食店の詳細情報や口コミの表示拡張。

③中間地点を算出にしているが、指定した分割ポイントの算出もしてみたい
例えば、A点とB点の1/4地点を算出（4ポイント）分を出力する
※これにより使えるユーザーの幅を広げられる。例えば旅行に車で向かう人やトラックの運転手など目的に向かうために挟む休憩点を算出に使える。

④中間地点の文字表示の他にMAPの表示

- UI・体験の改善：スマホからでもワンタップで自分の現在地や最寄り駅を登録できるようにする。
- 機能以外の工夫：飲み会の幹事の負担を極限まで減らす「お助けツール」としてのシェア機能。

### 10-2. 技術選定の比較検討

- 他にどんな技術を候補にしたか
- なぜその候補ではなく、この技術を選んだのか
- 不採用にした技術とその理由

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails (フレームワーク) | 採用 | カリキュラムで習得した強みを最大限に活かして素早くMVPを作るため |
| Node.js / Express (フレームワーク) | 不採用 | フルスタックの構成やルーティング・DB連携の仕組みをイチからキャッチアップする時間がかかるため |
| PostgreSQL (DB) | 採用 | Railsとの親和性が高く、位置情報（緯度・経度）を扱うデータ構造やクエリの知見を活かせるため |
| MySQL (DB) | 不採用 | 実績はあるが、今回の地理空間データや将来的な拡張性を考慮して使い慣れたPostgreSQLを選択するため |
| Render (デプロイ先) | 採用 | Renderは無料枠から手軽に使え、Railsアプリのデプロイ手順がシンプルでスムーズなため |
| AWS | 不採用 | AWSは初期設定や環境構築の学習コストが高いため今回は見送り |

- 今回チャレンジしたい点： 
  - 複数人の出発地データを受け取り、Rails側で「公平な中間地点の駅」を導き出す算出ロジックの実装
- 不安な点： 
  - アルゴリズムの設計や、意図した駅がうまく算出できなかった時のデバッグ作業

---

### 10-3.キャッチアップ不足の懸念

キャッチアップ不足の段階では以下の懸念点があります。

1. **完成までのハードルが高い**
Railsでの独自の算出ロジック（複数人のデータ処理やアルゴリズム設計）など、一筋縄ではいかない部分があるため一定の調査・学習時間を要する。

2. **Issueの見積もりが難しい**
算出ロジックの実装や、エッジケース（極端な位置関係のメンバーがいた場合など）で躓いた場合の切り分けに時間がかかる可能性がある。
